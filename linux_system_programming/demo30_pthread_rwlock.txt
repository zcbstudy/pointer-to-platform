==================================================
一、今天 demo30 的学习目标
==================================================

今天不是单纯记几个函数，而是要解决这些问题：

1. mutex 和 rwlock 到底有什么区别？
2. 读锁和写锁分别在“锁”什么？
3. 为什么多个 reader 可以同时进入？
4. writer 为什么必须等所有 reader 都退出？
5. 已经有 writer 等待时，后来的 reader 能不能继续进入？
6. 写锁和 mutex 很像，那 rwlock 的真正价值是什么？
7. 锁到底锁的是“变量”还是“访问权限”？
8. 为什么全局变量已经能直接修改，还要上锁？
9. 函数和线程到底有什么区别？
10. 线程加了锁以后，不还是一个一个执行吗？
11. 临界区到底应该多大？
12. 什么时候用 mutex，什么时候用 rwlock？
13. 读-改-写为什么必须放在写锁里面？
14. 为什么不能拿旧值 old 再覆盖最新共享状态？
15. 摄像头 / 多线程只读模型和 rwlock 有什么联系？

今天最重要的目标：

==================================================
二、先分清：mutex 和 rwlock 不是同一种锁
==================================================

普通互斥锁：

pthread_mutex_t mutex;

特点：

同一时刻只有一个线程能持有 mutex。

无论这个线程只是读，还是要写，
只要拿的是 mutex，其他线程都要等。


读写锁：

pthread_rwlock_t rwlock;

特点：

同一把 rwlock 有两种获取方式：

1. 读锁：
pthread_rwlock_rdlock(&rwlock);

2. 写锁：
pthread_rwlock_wrlock(&rwlock);

释放统一使用：

pthread_rwlock_unlock(&rwlock);


核心规则：

读 + 读
→ 可以并发

读 + 写
→ 不可以

写 + 读
→ 不可以

写 + 写
→ 不可以


==================================================
三、读锁和写锁到底“锁”的是什么？
==================================================

今天最容易混乱的点之一：

“锁里面是不是放着资源？”
“rwlock 里面是不是装了 data / AB？”

答案：

不是。

例如：

int AB = 100;
pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

内存概念上：

AB
→ 是共享变量

rwlock
→ 是另一个独立的同步对象

rwlock 里面没有装 AB。

程序员只是规定：

“凡是访问 AB 的线程，都必须遵守 rwlock 这把锁的规则。”

所以更准确地说：

锁控制的是：
“谁现在有资格访问这份共享资源。”

而不是：
“把资源物理装进锁里。”


学习阶段可以把“锁住资源”理解为：

“通过锁控制对共享资源的访问权限。”


==================================================
四、为什么读锁可以多个线程同时持有？
==================================================

假设：

int data = 100;

A、B、D 三个线程都只读 data。

例如：

pthread_rwlock_rdlock(&rwlock);

printf("%d\n", data);

pthread_rwlock_unlock(&rwlock);

A、B、D 都可以同时取得读锁。

原因：

它们都没有修改 data。

所以：

A 读 data
B 读 data
D 读 data

这三件事互相不会破坏对方的数据。


可以理解为：

data = 100

A 看 100
B 看 100
D 看 100

大家只是看，没有人改。


==================================================
五、为什么写锁必须独占？
==================================================

如果线程 C 要修改：

pthread_rwlock_wrlock(&rwlock);

data = 200;

pthread_rwlock_unlock(&rwlock);

C 一旦真正取得写锁：

其他 reader 不能进入
其他 writer 也不能进入

因为写操作可能改变共享状态。

因此：

writer 持有写锁
→ 所有人都要等


==================================================
六、writer 必须等“所有 reader”退出
==================================================

今天明确推过这个场景：

A：持有读锁
B：持有读锁
C：申请写锁

此时 C 不能写。

如果：

A unlock

但是：

B 还持有读锁

那么 C 仍然不能获得写锁。


必须：

A unlock
B unlock

也就是：

当前 reader 数量 = 0

之后 C 才有机会获得写锁。


核心结论：

写锁要求：

reader = 0
writer = 0

才能取得。


==================================================
七、A/B 正在读，C 等写，D 后来又读，会发生什么？
==================================================

今天的核心实验模型：

A：reader，已经持有读锁
B：reader，已经持有读锁
C：writer，已经申请写锁，但还没拿到
D：后来才申请读锁


这里需要区分：

1. C 只是“在等写锁”
2. C 已经“真正拿到写锁”

如果 C 已经真正拿到写锁：

D 一定不能读。
D 必须等 C unlock。


但是如果：

A、B 仍然持有读锁
C 还只是等待 writer
D 这时申请读锁

那么在当前 Linux/glibc 默认行为下，
D 仍然可能获得读锁并加入 A/B。


这会出现：

A 读
B 读
D 读
C 继续等写锁


所以：

writer 只是排队
≠
writer 已经独占


==================================================
八、为什么这会产生 writer starvation（写者饥饿）？
==================================================

如果一直有新的 reader 进来：

A 读
B 读
D 又来读
E 又来读
F 又来读
...

而 C 一直等待写锁。

只要系统一直没有出现：

reader 数量 = 0

C 就可能一直拿不到写锁。

这叫：

writer starvation
写者饥饿


注意：

饥饿 ≠ 死锁

死锁：

A 等 B
B 等 A
形成环形等待

饥饿：

C 理论上可以获得锁，
但别人一直抢在前面，
导致 C 很久甚至一直轮不到。


==================================================
九、写锁和 mutex 到底有多像？
==================================================

今天最后已经明确：

写锁在“独占”这一点上，
确实很像 mutex。

mutex：

一次只有一个线程进入临界区。

rwlock 的写锁：

一次也只有一个 writer，
并且 writer 存在时 reader 也不能进入。


所以可以粗略理解：

wrlock 的独占效果
≈
mutex


但 rwlock 真正比 mutex 多出来的能力是：

多个 reader 可以同时持有读锁。


因此：

如果大家几乎都是 writer：

A 写
B 写
C 写
D 写

那么 rwlock 最后全是：

pthread_rwlock_wrlock()

效果和 mutex 很接近。

这时 rwlock 没有发挥“读并发”的优势。


==================================================
十、什么时候选 mutex，什么时候选 rwlock？
==================================================

不要机械记：

“有读有写就用 rwlock。”

正确判断应该看访问模式。


情况 1：

大量修改
很少纯读取

例如：

A 写
B 写
C 写

这种：

mutex 往往更简单。


情况 2：

线程数量少
竞争很轻
临界区极短

即使有读有写，
mutex 也往往够用。


情况 3：

大量 reader
少量 writer

例如：

A 读
B 读
C 读
D 读
E 偶尔写

这种才是 rwlock 的典型场景。


核心：

rwlock 的价值是：

利用“多个只读线程可以同时访问”这一特点。


==================================================
十一、全局变量为什么不能直接改？
==================================================

今天一直绕的一个关键问题：

“我在函数里 AB = 999 不就行了吗？”
“为什么非要加锁？”

例如：

int AB = 100;

线程 A：

AB = 200;

main 线程：

AB = 999;


如果它们可能同时运行，
又没有任何同步：

这是 data race（数据竞争）。

不能靠猜：

“最后可能是 200”
“最后可能是 999”

来写程序。


真正的规则：

不是因为“有全局变量”就必须加锁。

而是：

多个线程
+
可能同时访问同一份共享数据
+
至少一个线程会修改

才需要同步。


==================================================
十二、main 也是线程
==================================================

今天容易忽略的一点：

main() 运行所在的执行流本身就是主线程。

所以：

工作线程 A 用 rwlock 保护 AB

但 main 线程直接：

AB = 999;

不加锁

那么 A 的锁就没有完整保护 AB。


如果规定：

“AB 由 rwlock 保护”

那么所有会并发访问 AB 的线程，
包括 main 线程，
都必须遵守同一把 rwlock。


==================================================
十三、锁不是让赋值语句“能执行”
==================================================

例如：

AB = 999;

即使没有锁，
这条 C 语句照样可以执行。


写锁真正负责的是：

“我修改 AB 的这段时间里，
其他遵守同一把锁的线程不能同时读/写 AB。”


所以：

AB = 999;
→ 负责修改数据

pthread_rwlock_wrlock(&rwlock);
→ 负责建立线程之间的并发秩序


这是两个完全不同的职责。


==================================================
十四、函数和线程到底有什么区别？
==================================================

今天另一个大的疑问：

“函数也是一个一个执行。”
“线程加锁以后不也是一个一个执行？”
“那线程和函数有什么区别？”


函数：

描述“要做什么”。

线程：

是独立的执行流。


普通单线程：

funcA();
funcB();

一定是：

A 全部执行完
→ B 才开始


多线程：

pthread_create(... thread_A ...);
pthread_create(... thread_B ...);

A 和 B 可以交错运行。

多核 CPU 上还可能真正同时运行。


==================================================
十五、线程有锁以后是不是也完全串行？
==================================================

不是。

锁只影响：

lock()
到
unlock()

之间的临界区。


例如：

线程 A：

calculate_A();      // 可并发

wrlock
AB = result;
unlock

other_work_A();     // 可并发


线程 B：

calculate_B();      // 可并发

wrlock
AB = result;
unlock

other_work_B();     // 可并发


真正串行的只有：

访问冲突的共享资源那一小段。


所以正确模型是：

A：自己的工作 ===== [短临界区] ===== 自己的工作
B：自己的工作 =====    [短临界区] == 自己的工作

大部分时间仍然可以并发。


==================================================
十六、如果整个线程都被锁住，会怎样？
==================================================

如果这样写：

lock

calculate_A();
AB = 200;
other_work_A();

unlock


而 B 也整个函数拿同一把锁：

那么：

A 整个做完
→ B 才开始

这种设计已经非常接近：

A();
B();

顺序执行。


而且多线程还有：

线程创建
调度
锁竞争

这些额外开销。

所以这种设计甚至可能比单线程更慢。


这也是为什么：

临界区不能乱放大。


==================================================
十七、临界区到底应该多大？
==================================================

今天最终结论不是：

“锁越少越好。”

而是：

在保证共享状态操作正确、完整、一致的前提下，
临界区尽可能小。


例如：

int result = very_slow_calculate();

如果 calculate 不依赖共享 AB：

可以：

int result = very_slow_calculate();   // 锁外

wrlock

AB = result;

unlock


这样：

耗时计算在锁外

真正修改共享 AB 的一瞬间才拿写锁。


==================================================
十八、读线程也应该尽量缩短临界区
==================================================

例如：

int local;

rdlock

local = AB;

unlock


然后：

printf("%d\n", local);
calculate(local);
sleep(...);

都可以放锁外。


因为：

local 是线程自己的局部副本。

AB 是共享变量。


对于普通 int：

local = AB;

是值复制。


之后即使其他线程：

AB = 999;

local 也不会自动变成 999。


==================================================
十九、如果计算依赖共享变量当前值，不能乱拆锁
==================================================

这是今天另一个非常重要的点。

如果操作是：

AB = AB + 100;

这实际上是：

读取 AB
→ 计算
→ 写回 AB

这是一个完整的：

read-modify-write
读-改-写


不能错误写成：

int old = AB;       // 锁外
int result = old + 100;

wrlock
AB = result;
unlock


因为 old 可能已经过期。


==================================================
二十、stale state（旧状态 / 过期状态）问题
==================================================

今天举过：

最开始：

AB = 100


线程 A：

old = AB;

所以：

old = 100


A 放锁以后，
线程 B：

AB = 500;


此时真正共享状态：

AB = 500


但是 A 最后：

wrlock

AB = old + 100;

unlock


由于：

old = 100

最后：

AB = 200


这就把 B 已经写入的 500 覆盖掉了。


如果业务真正要求：

“基于当前最新 AB 再 +100”

正确应该：

wrlock

AB = AB + 100;

unlock


如果 B 已经把：

AB = 500

那么 A 真正拿到写锁后：

读取当前 AB = 500
→ +100
→ AB = 600


==================================================
二十一、写锁里面可以读，也可以写
==================================================

今天还纠正了一个理解：

wrlock 不是：

“只能写不能读。”

wrlock 的真正含义是：

“我现在独占这份共享资源。”


所以持有写锁以后：

可以读取 AB
也可以修改 AB


因此如果操作本身是：

先读取当前 AB
再根据当前值修改 AB

直接拿写锁：

wrlock

读取 AB
计算
修改 AB

unlock


不需要：

先 rdlock
再 wrlock


==================================================
二十二、为什么不要拿着 rdlock 再申请 wrlock？
==================================================

错误思路：

rdlock

读取 AB

wrlock

修改 AB


此时当前线程自己已经持有读锁。

但 wrlock 要求：

所有 reader 都退出。

其中一个 reader 就是自己。

于是可能形成：

自己等自己释放读锁。


所以不能简单把：

读锁
→ 直接升级成写锁


如果一开始就知道要修改：

直接 wrlock。


==================================================
二十三、“先看看，可能要改”怎么办？
==================================================

可以先读：

rdlock

need_update = (AB < 100);

unlock


如果需要修改：

wrlock

再次检查当前 AB

if (AB < 100)
{
    AB = 100;
}

unlock


为什么要再次检查？

因为：

读锁释放
→ 到真正拿到写锁

中间可能有其他 writer 修改 AB。


所以：

之前看到的状态
≠
现在真正拿到写锁时的状态


==================================================
二十四、这里为什么用 if，不用 while？
==================================================

昨天 demo29：

while (ready == 0)
{
    pthread_cond_wait(...);
}

使用 while 是因为：

没有资源
→ 睡眠
→ 被唤醒
→ 状态可能仍然不满足
→ 所以反复检查


今天：

wrlock

if (AB < 100)
{
    AB = 100;
}

unlock


这里只需要：

拿到写锁后重新检查一次当前状态。

如果：

AB < 100
→ 修改

否则：
→ 不修改

没有“睡眠后反复等待同一个条件”的需求。

所以这里用 if。


==================================================
二十五、读写锁初始化 / 销毁
==================================================

静态初始化：

pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;


读锁：

pthread_rwlock_rdlock(&rwlock);


写锁：

pthread_rwlock_wrlock(&rwlock);


释放：

pthread_rwlock_unlock(&rwlock);


程序最后不用了：

pthread_rwlock_destroy(&rwlock);


注意：

unlock
→ 只是当前这次释放

destroy
→ 整个 rwlock 对象以后都不用了

二十六、今天 demo30 的完整实验代码
==================================================

#define _XOPEN_SOURCE 700

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

int data = 100;


/* 读线程 */
void *reader(void *arg)
{
    char name = *(char *)arg;

    printf("reader %c: want read lock\n", name);

    pthread_rwlock_rdlock(&rwlock);

    printf("reader %c: get read lock, data = %d\n",
           name, data);

    /*
     * 故意睡 4 秒。
     *
     * 这是为了教学观察：
     * 让 A/B 长时间持有读锁，
     * 好观察 writer C 和后来 reader D 的行为。
     *
     * 真正工程中一般不会故意长时间持锁。
     */
    sleep(4);

    printf("reader %c: unlock\n", name);

    pthread_rwlock_unlock(&rwlock);

    return NULL;
}


/* 写线程 */
void *writer(void *arg)
{
    char name = *(char *)arg;

    printf("writer %c: want write lock\n", name);

    pthread_rwlock_wrlock(&rwlock);

    printf("writer %c: get write lock\n", name);

    data = 200;

    printf("writer %c: data = %d\n",
           name, data);

    sleep(1);

    printf("writer %c: unlock\n", name);

    pthread_rwlock_unlock(&rwlock);

    return NULL;
}


int main(void)
{
    pthread_t tid_a;
    pthread_t tid_b;
    pthread_t tid_c;
    pthread_t tid_d;

    char a = 'A';
    char b = 'B';
    char c = 'C';
    char d = 'D';

    /*
     * A、B 先启动 reader。
     */
    pthread_create(&tid_a, NULL, reader, &a);
    pthread_create(&tid_b, NULL, reader, &b);

    /*
     * 教学实验用。
     * 尽量让 A/B 先取得读锁。
     */
    sleep(1);

    /*
     * C 后来申请写锁。
     */
    pthread_create(&tid_c, NULL, writer, &c);

    /*
     * 尽量让 C 先进入等待写锁状态。
     */
    sleep(1);

    /*
     * D 最后申请读锁。
     */
    pthread_create(&tid_d, NULL, reader, &d);


    pthread_join(tid_a, NULL);
    pthread_join(tid_b, NULL);
    pthread_join(tid_c, NULL);
    pthread_join(tid_d, NULL);

    pthread_rwlock_destroy(&rwlock);

    return 0;
}

二十八、今天实际跑出的关键结果
==================================================

为了保证实验现象明显，
reader 持有读锁 sleep(4)。

实际运行输出：

reader A: want read lock
reader A: get read lock, data = 100
reader B: want read lock
reader B: get read lock, data = 100
writer C: want write lock
reader D: want read lock
reader D: get read lock, data = 100
reader A: unlock
reader B: unlock
reader D: unlock
writer C: get write lock
writer C: data = 200
writer C: unlock


==================================================
二十九、这个输出证明了什么？
==================================================

时间线：

1. A 得到读锁
2. B 得到读锁

所以：

A + B 同时读


3. C 申请写锁

但是：

A/B 仍然在读

所以：

C 等待


4. D 后来申请读锁

这次实验里：

D 仍然取得读锁


于是：

A + B + D 同时读
C 继续等


5. A unlock
6. B unlock

但是如果还有 D 在读：

C 仍然不能写


7. D unlock

此时：

所有 reader 都退出


8. C 才取得写锁
9. C 修改 data = 200
10. C unlock


==================================================
三十、pthread_create 的书写顺序不等于线程绝对执行顺序
==================================================

例如：

pthread_create(&tid_a, ...);
pthread_create(&tid_b, ...);
pthread_create(&tid_c, ...);

不代表运行时一定：

A 完整执行
→ B 完整执行
→ C 完整执行


pthread_create 只是创建独立线程。

实际线程什么时候获得 CPU，
什么时候执行到 rdlock / wrlock，
受调度影响。

==================================================
三十一、同一个 reader() 函数可以被多个线程同时执行
==================================================

今天也绕过这个问题：

A、B、D 都调用：

void *reader(void *arg)

会不会出问题？


不会因为“同一个函数”本身出问题。


线程 A：

有自己的线程栈
自己的函数调用现场
自己的局部变量


线程 B：

也有自己的线程栈
自己的函数调用现场
自己的局部变量


真正需要同步的是：

它们共同访问的共享数据。


所以：

同一个函数
≠
只能一个线程执行


==================================================
三十二、局部变量和共享全局变量
==================================================

例如：

void *reader(void *arg)
{
    int temp;
}

A 调用 reader：

A 有自己的 temp

B 调用 reader：

B 有自己的 temp


它们不是同一个 temp。


但是：

全局：

int data = 100;

对于同一个进程里的 pthread：

A/B/C/D 看到的是同一个 data。

==================================================
三十六、今天最容易说错的几个词
==================================================

1.

错误直觉：
“把资源放进锁里面”

正确：
资源和锁是独立对象，
锁控制访问共享资源的权限。


2.

错误：
“A 把锁交给 C”

更准确：
A 释放自己的锁状态；
C 之后有机会竞争并获得锁。


3.

错误：
“写锁只能写”

正确：
写锁表示独占。
持有写锁时既可以读，也可以写。


4.

错误：
“线程用了锁就完全变串行”

正确：
只有冲突的临界区串行；
锁外代码仍然可以并发。


5.

错误：
“有全局变量就必须锁”

正确：
存在并发访问，并且至少有一方修改时，
才需要同步。


6.

错误：
“有读有写就必须 rwlock”

正确：
rwlock 更适合读多写少。
简单场景 mutex 往往更直接。

==================================================

mutex：

所有冲突访问都一个一个来。


rwlock：

三十九、demo30 工程核心
==================================================

真正要学会的不是：

pthread_rwlock_rdlock()
pthread_rwlock_wrlock()
pthread_rwlock_unlock()

而是：

1. 识别共享数据
2. 判断哪些线程只读
3. 判断哪些线程会修改
4. 判断访问是否真正并发
5. 选择 mutex 还是 rwlock
6. 正确划定临界区
7. 避免旧状态覆盖新状态
8. 不依赖线程执行顺序
9. 不把整个线程都锁成串行
10. 让没有冲突的工作尽量并发

==================================================
四十一、今天需要真正记住的几句话
==================================================

1.
锁不保存资源。
锁控制线程访问共享资源的权限。

2.
多个 reader 可以同时持有读锁。

3.
writer 必须等所有 reader 都释放，
才能获得写锁。

4.
writer 真正持有写锁以后，
其他 reader 和 writer 都不能进入。

5.
写锁在独占效果上很像 mutex。

6.
rwlock 真正的价值是：
读多写少时，可以让多个 reader 并发。

7.
线程不是整个函数都必须串行。
只有 lock 到 unlock 的冲突临界区需要等待。

8.
共享状态的 read-modify-write
必须作为一个整体保护。

9.
如果修改依赖“当前最新值”，
不要拿锁外保存的旧值直接覆盖。

10.
在保证正确性的前提下，
临界区尽可能短。

11.
mutex / rwlock 的选择不是看哪个“高级”，
而是看实际读写模式和竞争情况。

12.
最终目标不是背锁函数，
而是写出并发正确、性能合理、能解决实际问题的程序。
